> 端到端流程 · 工具索引 · 跨领域规则见 [`PLAYBOOK.md`](./PLAYBOOK.md);本文管单间设计。

## 0. 铁律

1. **一间做到位并通过用户验收,才允许开下一间。** 没完成不碰下一间。
2. **每间做完必须往 §3 手法库沉淀经验**,让后一间比前一间做得好。这是本方法存在的意义。
3. **顺序**:先四主屋 polish(它们是基准,也是手法的试验场)→ 手法沉淀成熟 → 再逐间做村民房。
4. 36 间村民房已于 2026-07-19 完全清空,旧内容一律不作参考。

## 0.5 完成标准 ★★ 2026-07-19 用户纠偏 —— 先读这条再动手

用户原话:「**空不是问题，设计上是需要保留空气感的。完成的标准不是填满，而是他是一间合适角色身份、爱好、功能的屋子，布局合理**」

### 完成 = 满足这三条,而不是填满
1. **身份契合** —— 这间屋子一眼看去就是**这个角色**的:他的职业、爱好、生活习惯都在物件里有据可循
2. **功能成立** —— 他在这里真的能干活、能生活;器物的种类和位置服务于他的工作流
3. **布局合理** —— 家具关系说得通,动线通畅,空间有主次

### 空气感是设计元素,不是缺陷
- **留白是正当的**,不需要被填掉。空地、留空的墙面、没有摆满的角落都可以是有意的
- **不要把"某处很空"当成待办事项**。判断依据是"这里空着合不合理",不是"这里空着"
- 一间屋子的疏密应该有**节奏**:工作区密、活动区疏,而不是均匀铺满

### ✗ 已经犯过的错(不许重犯)
- 把"陈设数量"当质量指标(D2.0 的密度标准)→ 造出撒点垃圾
- 看到空地就想填 → 撒抽象小点、复制坐标数组、整齐排列同一物件凑数
- **本方法一切以"合适"为准,不以"多"为准**

> 注:§3 的 T1 物件分层解决的是**单个物件的质感**(为什么看起来平),
> 跟"要不要更多物件"是两回事,不要混为一谈。物件少而精 + 每个都分层 > 物件多而平。

## 1. 单间工作流程

每间房固定走这 6 步,**不允许跳步**:

### S1 立项(动笔前)—— 这一步决定成败,不许省
回答三问(对应 §0.5 的三条完成标准):
1. **身份**:他是谁?职业、性格、爱好、生活状态?什么细节只有他会有?
2. **功能**:他在这屋里的一天怎么过?工作流是什么?需要哪些器物才干得成活?
3. **布局**:哪里是工作区、储物区、生活区、通道?疏密节奏怎么安排?**哪里应当留空**?

- 列出器物清单,按功能分组;**宁可少而准,不要多而泛**
- 产出:3-5 句设计意图 + 器物清单 + 疏密规划。**给用户看,确认了再动手**

### S2 平面图(纯坐标,先于任何绘制)
- 把家具写成矩形表 `[name, x, y, w, h]`
- 跑 `tools/planlint.py` 校验,**必须 0 违规**才能动笔:
  - P1 家具矩形之间零重叠
  - P2 不进门口禁区(y+h>2280 且 x 跨 420-1020)—— 被出门/行动按钮遮挡
  - P3 不进顶栏禁区(y<180)—— 被标题栏遮挡
  - P4 通道宽度 ≥80px(角色要走得过去)
- 产出:通过校验的平面图

### S3 骨架
- 按平面图画家具外形,每件**必须落在自己的矩形内**
- 每件**必须有落地投影**(证明它站在地上,不是浮着)
- 截图检查:空间关系是否成立、有没有莫名其妙的邻接

### S4 内容(注意:不是"填满")
- 每个物件按 §3 T1 **分层画到位**(3-7 层),质感来自分层,不来自数量
- 容器里放**对的东西**:书架放他会读的书、柜子放他工作要用的料
- 案面是"**刚用过**"的状态组合,不是陈列柜
- 散物必须有**来源和归属**:桌边掉的纸只在桌边,炭盆旁才有灰
- **严禁**往地面撒抽象小点冒充密度(上一轮的主要垃圾来源)
- **留白按 S1 的疏密规划保留,不要临时起意去填**

### S5 自检
- 跑 `planlint.py` 复检(填充可能引入新家具)
- 带 UI 截图:`node tools/shot.js <绝对路径> '<选择器> .screen' 'name:4'`
- **必须带 UI 截图**,否则看不出被按钮/标题栏遮挡

### S6 验收 + 沉淀
- 自问 §0.5 三条:身份契合?功能成立?布局合理?(**不问"够不够满"**)
- 把截图给用户看,等明确通过
- 通过后:①往 §3 手法库写这间学到的技法 ②commit ③才能开下一间
- 未通过:回到对应步骤重做,**不进下一间**

## 2. 质量门禁(可机械检测的部分)

`python3 mini/tools/planlint.py` —— 必须 0 违规。

机器只能测空间违规,**测不出美术水准,更测不出"合不合适"**。门禁通过 ≠ 合格,还要过 S6 人工验收。
注意 planlint **不含任何密度/数量指标**,以后也不要加 —— 数量不是质量。
这一点是上一轮的血泪:planlint 全绿的 shenyan / orlando,用户看了仍然不满意。

## 3. 手法库(每完成一间就往这里加)

> 这一节是本方法的核心资产。写**具体可复用的技法**,不写空话。
> 格式:【技法名】问题 → 做法 → 代码要点

### T1 【物件分层】★最重要 —— 这是四主屋和废弃村民房的根本差距

**问题**:村民房的物件"怎么画都平、都像贴纸",堆再多也没质感。
**根因**:一个物件只画 1-2 层 `fillRect`。四主屋每个物件画 **3-7 层**。

**做法**:任何物件从外到内至少 3 层,重要物件 5-7 层:

| 层 | 内容 | 要点 |
|---|------|------|
| ① 投影 | 同形状,下移 3-5px,`rgba(50,35,18,0.22)` | 让物件"站在地上"而非浮着 |
| ② 描边 | 深色,最大尺寸,`#3a2c20`/`#4a3626` | **像素画的立体感全靠它**,不可省 |
| ③ 主体 | 内缩 3-4px,物件固有色 | |
| ④ 高光 | 边缘或上沿亮一档 | 体现光源方向(本项目光从上来) |
| ⑤ 暗部 | 内圈/下沿暗一档 | |
| ⑥⑦ 细节 | 缝线/纹样/磨损/刻度 | 少量即可,位置要有理由 |

**基准实现**(阿云房蒲团,7 层):
```js
pxCircle(x, y+4, 30, 'rgba(50,35,18,0.22)')  // ① 投影
pxCircle(x, y,   30, '#3a2c20')              // ② 描边
pxCircle(x, y,   26, '#8a9ab8')              // ③ 主体
pxRing  (x, y, 26, 4, '#a8b8d0')             // ④ 边缘高光
pxRing  (x, y, 16, 2, '#5a6a88')             // ⑤ 内圈暗纹
pxCircle(x, y,  8,    '#5a6a88')             // ⑥ 中心
for(let a=0;a<8;a++) fillRect(...)           // ⑦ 缝线 8 点
```
矩形物件同理:先画深色大矩形,再内缩 3px 画主体色。

### T2 【工具函数库】—— 村民房完全没有,必须先建

四主屋自带一套工具,村民房是裸 `fillRect`,这是差距的技术来源:

```js
pxCircle(cx, cy, r, color)          // 像素圆(逐行 fillRect,无抗锯齿)
pxRing(cx, cy, r, w, color)         // 像素环
box(x, y, w, h, edge, fill)         // 自带描边的矩形 = 深色底 + 内缩 3px 填充
glow(x, y, r, color)                // 径向渐变发光(灯/烛/火)
spr(name, x, y, scale)              // ASCII 字符串定义的精灵图
```
**新房间开工第一件事是把这套工具准备好**,不要用裸 `fillRect` 硬画圆。

### T3 【统一色板】—— 不要每次手写十六进制

四主屋用常量色板,同一房间的所有物件从中取色,因此整体协调:
```js
const C = { K:'#3a2c20', N:'#a06a40', n:'#7e5230', W:'#f6efdc',
            Y:'#ffd76a', y:'#e8b23d', Z:'#9a938a', z:'#6e675e',
            F:'#f0c8a0', E:'#4a3626', H:'#4a3a2c', B:'#5a7a96',
            O:'#e89040', R:'#d05848' }
```
规律:大写=亮版,小写=暗版,成对出现(N/n、Y/y、Z/z)。
**每间房定 10-14 色的板,不够用再加,不要随手写新颜色** —— 上一轮村民房颜色失控是"脏"的来源之一。

### T4 【重复物件用局部函数,不用复制坐标数组】

四主屋写法:
```js
function coin(x, y) { pxCircle(x,y,7,'#e8b23d'); pxRing(x,y,7,1,'#a87820'); ... }
coin(300,640); coin(316,648); coin(290,654)
```
上一轮村民房的错误写法:复制一个 20 项坐标数组,换个名字当新物件。
**规则**:同类物件写成函数 + 少量调用点,每个调用点位置要有现实理由(为什么这枚铜钱掉在这)。

### T5 【坐标系】四主屋用 720×1080 + `g.scale(2,2)`

等效像素粒度更粗、更整齐,像素感更强。村民房用的是 1440×2560 裸坐标,单像素太细,细节糊成一团。
**新房间沿用四主屋的 scale(2,2) 方案。**

### T6 【新增角色姿态】头部复用 + 身体对齐头轴

**问题**:给角色加新姿态(卧姿/坐姿/特殊动作)时另画一个头,角色就不像同一个人了。

**做法**:
1. **头部整段复用**既有姿态,朝上/朝前取 `stand`、朝侧取 `standside`,**只新画脖子以下**
2. **身体对齐该头的中轴**——站姿头轴在第 6.5 列、侧站头轴在第 5 列,各不相同,不能按 sprite 居中想当然
3. 宽度不够时**加宽身体,不要挪头**(挪位是身体迁就头,加宽是身体包住头)
4. 容差:**半列(4px @scale8)偏移就会读成歪脖子**
5. 姿态数据只在 `pdef` 处写一次 —— 角色资源**引用** `window.AYUN_POSES` 而非拷贝(旧版是拷贝式,漏写一边会静默回退成 `stand`,已从根上消除)

**实证**:阿云卧姿初版自画了头(脸更窄、无发髻鬓角),床上像另一个人;修正后又因被子按 sprite 居中而歪脖子。完整规范见 design.html B0 「POSE AUTHORING」。

### T7 【剪影优先】—— 角色/动物不像,先查剪影不查细节

不像猫,几乎总是这四条没立住,而不是细节不够:**耳**(分开的实心三角,不是孤立描边点)、**颈**(头身之间收窄一格)、**尾**(接近体长、沿一侧上翘)、**腿**(两腿间留空隙)。错的剪影加多少细节都救不回来。

小动物**不按真实比例**。真猫是人的 1/3,在 scale 8 下只剩 5 格高,画不出可辨识的猫。放大到约 2/3 —— 这是像素游戏的通行解,不是妥协。

**像素颗粒必须全局一致**(所有角色同 `scale`),这条优先于构图。

### T8 【落地点从 sprite 算,不写字面量】

固定 `foot` 只在所有姿态同尺寸时成立;姿态尺寸有差异就用 `footMode: 'bottom'`,按 sprite 自身底边中心落地,换 scale 也不用重算。

锚点→脚点的换算**不许写字面量** —— 写死一次会散到二十几处,改尺寸时漏一处就错位。从 `ACTORS[id].foot` 读。

### T9 【交互反馈只落在自己的像素上】

命中逐像素(组合件包围盒常远大于实际像素);反馈不画框,把素材自身 sprite 以 `lighter` 叠一层。**不要用包围盒驱动光晕** —— 按 `max(w,h)` 算半径会照亮一大片空气,把逐像素命中的意义整个抵消。

### T11 【火 · 烟 · 能量体】—— 形错了，改色救不回来

三种效果各有一条决定性的「形」，颜色只是次要：

- **火** = 下宽上尖的**舌**，逐行收窄，三层焰心不同频率摇曳。**高宽比至少 1.3:1** —— 宽大于高会摊成圆拱，读作余烬不是在烧的火。画成矩形上下缩放，再橙也是一块布
- **一簇 vs 一堆**：单簇要窄而高；确实要一堆时，几簇之间必须错开 `seed`，并在底下垫一层宽而矮的橙红把火根焊住，否则是几根蜡烛并排
- **烟** = **一团由三个错位的圆叠成**，不是一个圆；边升边胀、尾段快淡。漂移用**两个不同频率的正弦叠加** —— 单一正弦会走出整齐的蛇形，一眼假。画成方块就像纸片在飞
- **旋涡** = **亮核 + 丝缕状流带 + 暗底**。三样缺一不可：
  - **中心是最亮的**，不是黑洞也不是均匀的雾 —— 能量从核心甩出去，所以核心最亮（参考实拍：蓝色能量球、紫蓝星系旋涡皆如此）
  - **臂是一束丝不是一根管**：每条臂拆成 6–8 股，各自错开相位、粗细不一、亮暗混编，再加一点法向飘动。单股粗实的弧线读作橡胶管
  - **必须有暗底**：旋涡是发光体，没有暗的东西衬，亮部浮不出来。亮丝要**压过背景**——亮暗均摊的话整条臂比墙还暗，像一条紫绳搭在墙上
- **能量体（弥散型）** = **没有边界**，边由能量自己衰减出来。**浓度靠多个不规则雾团叠加堆出来，不靠底雾铺一层** —— 铺底会把团与团的层次糊平，越铺越像一块均匀的屏。团要抱成一团转，摊开就成了雾；半透明叠加会整体提亮，所以**色阶要压深**，用亮紫叠出来是一片发白。整体**歪一点**，正着摆就像挂了面镜子

一律走引擎原语 `fxFlame` / `fxSmoke` / `fxAura`，不要在素材里自己画。

- ~~底部 y2150+ 大面积留白是缺陷~~ ← **已被用户否定(2026-07-19)**:空是设计,不是待办。

### T12 【动画件】—— 静止时必须与原样【逐像素一致】

家具要动(木人被打会转、抽屉被拉会开、屏幕会闪),走 `variant(state, t)` 而不是 `fx`:
`variant` 换的是**实体 sprite**(走缓存、参与 y-sort、命中检测认得它),`fx` 是叠在上面的光效层
——**实物放进 fx 就等于不存在**(变体缓存、命中、视觉回归全以 `draw()` 为准,见事故模式 14)。

**做法**:把要动的那几笔**参数化**,静止时的参数值让它画出与改造前**完全相同**的像素。

```js
variant(st, t) { return (st && st.dummy) ? ('r' + (((t / 110) | 0) % 6)) : null },
draw(g, o) {
  const ang = ((o && o.variant) ? +o.variant.slice(1) : 0) * Math.PI / 3   // 无 variant → 0 → 原样
  …按 ang 画那几笔
}
```

**判据:改完先跑 `regress`。** 静止场景的指纹**必须不变** —— 变了就说明你顺手改了原画。
咏春木人桩这次差 2px 就被抓出来(右臂端头圆心原本回缩 2px,是原作者的手感,不是 bug)。

**旋转怎么画**:绕竖轴转的杆件,2D 上就是**水平投影收放 + 过零换边** ——
伸长 → 缩短 → 正对观者(只剩端头,给个最小长度别凭空消失)→ 从另一侧长出来。
三根臂固定在同一根转动的桩身上,所以**同步**换边,不要各转各的。

**状态谁来置**:房间 loop 里 `roomState(room, { dummy: st.mode === 'act' && !!st.act.dummy })` ——
**站定开打那一刻**才置,不是走过去的路上(否则人还在半路,桩已经自己转起来了)。

### T10 【成对物件】—— 把分界线做成对照，而不是做成切分

阿云的分界线是「一件 vs 全屋」，桃桃是「左右两半」，两者都靠**切空间**。
婆婆的两半叠在一起（她给别人的和她自己的是同一张桌子上的东西），切不开，
于是改用**成对物件**：每件「给别人的」旁边放一件「她自己的」，后者永远更旧、更少、更破。

三条要求，缺一条这个手法就不成立：

1. **两件必须落在同一视野内**。玩家不该走到房间另一头才发现对比 —— 走过去的路上对照就断了。
   婆婆房六对全部同框：糖罐↔碗、茶具↔缺口杯 同在待客桌；毛衣堆↔披肩 同在摇椅区；
   新牌↔旧牌 同在读牌桌（一个在桌面，一个在桌肚的抽屉里）。
2. **差异要做在同一个属性上**，不能这件比数量、那件比新旧。婆婆房统一比「多 / 新 / 全」对「少 / 旧 / 破」：
   糖罐满到盖不上 ↔ 碗只有一只；茶具四杯成套 ↔ 她的杯子豁了口；毛衣堆成山 ↔ 披肩磨穿了没换。
3. **「她没有」也要画成一件实物**。第四对是「挂满的御守 ↔ 她自己没有」——「没有」画不出来，
   于是把对照做进**单件素材内部**：一排七个钩子，前六个挂满，第七个只剩一个空绳圈和一枚没写字的木牌。
   空钩就是那件实物。
   ⚠ 这一格第一版只画了 4px 的浅印子，缩到实际尺寸完全看不见 —— **整间房的立意压在这一格上，
   它必须是能一眼认出的形状**，不是一处暗示。

配套：核心那一对给 `sayDeep`（追问三次才说的真话），并让「她自己的」那件是**有状态**的
（婆婆房的抽屉：关着时说「这个呀……里头没什么」，点开才看见旧牌）。
